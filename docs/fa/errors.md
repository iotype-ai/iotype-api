# خطاها و پایداری

## آنچه مستند شده

`401 Unauthorized` تنها کد وضعیتی است که در مستندات رسمی نام برده شده. این کد چهار وضعیت متفاوت را پوشش می‌دهد:

۱. هدر `Authorization` ارسال نشده
۲. توکن ساختار درستی ندارد
۳. توکن منقضی شده
۴. **اعتبار توکن تمام شده است**

هر چهار حالت را در پیام خطای خود پوشش دهید. کاربری که اعتبارش تمام شده و پیام «توکن نامعتبر» می‌بیند، وقتش را صرف بررسی مسئله‌ی اشتباهی می‌کند.

## آنچه مستند نشده

موارد زیر در [`spec/openapi.yaml`](../../spec/openapi.yaml) با علامت `x-unverified` مدل شده‌اند، چون استنتاجی هستند نه منتشرشده:

| کد | معنی محتمل |
| --- | --- |
| `402` | اتمام اعتبار توکن |
| `404` | `uuid` ناشناخته |
| `413` | حجم آپلود بیش از حد مجاز |
| `422` | خطای اعتبارسنجی در یکی از فیلدها |
| `429` | عبور از محدودیت نرخ درخواست |
| `5xx` | خطای سمت سرور |

کدی ننویسید که به این کدهای دقیق وابسته باشد؛ به‌جای آن روی بازه‌ها شرط بگذارید.

## بدنه‌ی خطا

هیچ ساختاری برای بدنه‌ی خطا منتشر نشده است. API ظاهراً بر پایه‌ی Laravel ساخته شده که قراردادش این است:

</div>

```json
{
  "message": "The given data was invalid.",
  "errors": { "file": ["The file field is required."] }
}
```

<div dir="rtl">

این را محتاطانه پارس کنید:

</div>

```python
try:
    detail = response.json().get("message")
except ValueError:
    detail = response.text[:500]
```

<div dir="rtl">

هرگز اجازه ندهید خطای پارس JSON، کد وضعیت اصلی HTTP را پنهان کند.

## سیاست تلاش مجدد

درخواست‌های ناموفق **توکن مصرف نمی‌کنند**، بنابراین تلاش مجدد روی خطای گذرا فقط زمان می‌برد.

| کد | تلاش مجدد؟ |
| --- | --- |
| `408`، `429`، `5xx` | بله، با backoff نمایی و jitter |
| timeout شبکه، قطع اتصال | بله |
| `400`، `401`، `403`، `404`، `413`، `422` | خیر — درخواست بدون تغییر موفق نخواهد شد |

سیاست پیشنهادی: ۳ تلاش، با فاصله‌ی ۱ ← ۲ ← ۴ ثانیه، به‌علاوه‌ی jitter تا ۲۵۰ میلی‌ثانیه.

**در تلاش مجدد آپلود احتیاط کنید.** درخواستی که سمت کلاینت timeout شده، ممکن است سمت سرور پذیرفته شده باشد. پیش از آپلود دوباره، `POST /io/v1/files` را صدا بزنید و ببینید فایلی با همان `filename` ساخته شده یا نه.

## Timeout

| endpoint | مقدار پیشنهادی |
| --- | --- |
| `/io/v1/translate` | ۳۰ ثانیه |
| `/io/v1/synthesis` | ۶۰ ثانیه |
| `/io/v1/transcribe/instant` | ۱۲۰ ثانیه |
| `/io/v1/transcribe` و `/io/v1/ocr` | ۱۲۰ ثانیه برای **آپلود** |
| `/io/v1/files` و `/io/v1/file/track` | ۳۰ ثانیه |

آپلود به endpointهای ناهمزمان سریع برمی‌گردد. آنجا timeout بلند نگذارید به این امید که نتیجه برسد — نتیجه روی آن اتصال نمی‌آید. باید polling کنید.

## خطاهای WebSocket

| نشانه | علت محتمل |
| --- | --- |
| بلافاصله پس از باز شدن بسته می‌شود | پیام Initialize ارسال نشده یا ناقص است، یا صوت زودتر فرستاده شده |
| وسط جلسه بسته می‌شود | انقضای توکن (Flash Token کوتاه‌عمر است)، قطعی شبکه، یا اتمام اعتبار |
| هیچ نتیجه‌ای نمی‌رسد | صوت به‌صورت فریم باینری فرستاده نشده، یا Base64 شده |

با backoff دوباره وصل شوید و در هر اتصال مجدد یک Flash Token تازه بسازید — این توکن‌ها یک‌بارمصرف‌اند.

صوت ضبط‌شده در زمان قطعی را بافر کنید، اما اندازه‌ی بافر را محدود نگه دارید. از دست دادن صوت قدیمی بهتر از تمام شدن حافظه در یک قطعی طولانی است.

## لاگ‌برداری

کد وضعیت HTTP، آدرس endpoint و مقدار `uuid` پردازش‌های ناهمزمان را لاگ کنید. **هرگز هدر `Authorization` را لاگ نکنید.** پیش از آنکه خروجی دیباگ HTTP به سامانه‌ی جمع‌آوری لاگ برسد، این هدر را حذف کنید.
